# 會考複習總覽：雲端同步與老師端安全說明

範圍：`index.html`（學生端同步、老師端唯讀檢視）＋`supabase/001_hk.sql`（表、RLS、RPC）＋`supabase/002_verify_hk.sql`（權限驗證）。
Supabase 專案沿用「統測單字 SRS App」那一個（`knsdpvmhloobfduhfwyk`），只新增 `hk_` 開頭的表與函式，不改動 `srs_` 的任何東西。

## 一句話
學生沒有帳號：老師給的連結裡有一串 122 bits 的隨機代碼，雲端只存它的 SHA-256 指紋。
學生端（anon）**碰不到任何一張表**，只能呼叫 `hk_load` / `hk_save` 兩個函式，函式用代碼找到「自己」才動作。
老師用 SRS App 的同一組 Supabase 帳號登入，而且必須在 `hk_teachers` 名單上才讀得到東西；老師端只能「看」，不能改學生的進度。

## 角色與權限

| 身分 | 能做 | 不能做 |
|---|---|---|
| anon（學生端、或任何拿到網頁裡 anon key 的人） | `hk_load(代碼)`、`hk_save(代碼, 進度列, 排程列)`：只對「代碼對得上的那位學生」有效 | 讀寫任何表（四張表都 `revoke all`，也沒有 anon policy）；建學生、重設連結、`hk_is_teacher` 都沒有 EXECUTE 權限 |
| authenticated 且在 `hk_teachers` | 讀 `hk_students`（只有 id/nickname/created_at/last_seen_at/link_reset_at，**不含** token_hash）、讀 `hk_progress`、`hk_plan`；`hk_create_student`、`hk_reset_link` | 直接寫任何表；讀 `hk_teachers` |
| authenticated 但不在名單 | 什麼都讀不到（RLS 回 0 列）；呼叫老師 RPC 會被 `42501` 擋 | — |
| service_role / SQL Editor | 全部（Supabase 管理者） | — |

所有函式都是 `security definer` ＋ `set search_path = ''`，表名全部寫成 `public.xxx`，避免被同名物件劫持。

## 連結（代碼）的一生
1. 老師端按「新增學生」→ `hk_create_student` 在資料庫裡用 `gen_random_uuid()` 產生 32 個十六進位字，只存 `sha256(代碼)`，代碼本身**只回傳這一次**。
2. 老師把 `…/?s=代碼` 私訊給學生（或家長）。
3. 學生點開：App 在**還沒抓任何資料之前**就把 `?s=` 從網址列拿掉（`history.replaceState`），代碼存進這台的 localStorage（`huikao.sync`）。
   另外：`<meta name="referrer" content="no-referrer">`；Service Worker 不把有 `?` 的網址存進快取（代碼不會留在快取裡）。
4. 之後每次同步都把代碼交給 `hk_load` / `hk_save`，資料庫比對指紋。
5. 連結外流 → 老師端「重設連結」→ 指紋換掉，舊連結立刻失效，雲端進度不受影響；學生用新連結開一次就接回（同一位學生不會跳出詢問）。

## 老師看得到什麼
- 學生名單：暱稱、最後一次成功上傳的時間、紅色（1–2 分）節數、逾期卡數。
- 點進某位學生：跟學生同一套「總覽／章節／計畫／今天」畫面，**唯讀**（所有改資料的按鈕都擋掉、`save()` 在唯讀模式直接不做事，學生資料不會寫進老師這台的 localStorage）。
- 看不到：連結代碼（只有指紋，而且指紋欄位老師也讀不到）。
- 隱私原則：只存暱稱，不存全名、學校、電話。

## 威脅模型

### T1 學生連結外流（例：學生把連結貼到群組）
- 後果：拿到連結的人可以讀、改**這一位**學生的熟悉度與排程。讀不到其他學生、讀不到老師資料。
- 降低方法：重設連結（見上）；暱稱不放真名。
- 剩餘風險：連結本身就是密碼，沒有第二道驗證（設計上就是免登入）。**沒有每日備份**（SRS App 有、這裡沒做）：被亂改只能靠學生自己的裝置再改回來。資料量很小（58 節＋幾百張卡），日後要補備份表很容易。

### T2 anon key 公開（網頁原始碼看得到）
- anon key 本來就設計成公開的；它只代表「anon 身分」。上表 anon 能做的事，全部都要先有正確代碼。
- 程式碼裡沒有、本次工作也沒用到 service_role key。

### T3 猜代碼
- 122 bits 隨機；格式先用 `^[0-9a-f]{32}$` 檢查，不對直接回 `invalid_link`。
- 只存 SHA-256 指紋：資料庫內容外洩也反推不出可用連結。對高熵隨機代碼，快速雜湊就足夠。

### T4 惡意或超大的上傳
- `hk_save` 檢查每一列：只准指定欄位；章節 id `^[a-z0-9-]{1,40}$`、卡片 id `^[a-z0-9]{1,40}$`、日期 `YYYY-MM-DD` 且真的存在（2026-02-30 會被拒）、分數 1–5 或空、次數 0–99999 整數、時間是整數毫秒；同一筆裡不能重複。任何一列不對 → **整筆拒收**（不會寫一半）。
- 數量：單次 ≤ 200 列進度、≤ 2000 張卡；每位學生總數 ≤ 1000 列進度、≤ 5000 張卡（含已刪除）；大小 ≤ 200 KB／1 MB。
- 卡片的主鍵是（學生, 卡片 id）：就算兩位學生用了一樣的卡片 id，也只會動到自己的。
- **未來時間**：合併是「時間新的贏」，所以有人可能故意送 9999 年讓那一列永遠蓋不掉。伺服器把時間最多壓到「現在＋10 分鐘」，10 分鐘後正常修改就蓋得過。
- App 端收到雲端資料時再清洗一次（`cleanRemote`）：形狀不對的列直接丟掉；章節表查詢用沒有原型的物件（`constructor` 之類的怪 id 查不到東西）。

### T5 洗版、頻率
- 同一位學生 1 秒內只收一次寫入（`too_fast`，App 會 3 秒後重送）；App 本身是改完 2 秒才送，而且只送改過的列。
- `hk_save` 先鎖住該學生那一列（`for update`），兩台同時送也不會算錯總數上限。
- 剩餘風險：Postgres 層沒有「每個 IP 幾次」的限流；大量亂打只能靠 Supabase 平台本身。對 1–2 位學生的家教 App 可接受。

### T6 學生端資料顯示在老師畫面（stored XSS）
- 老師畫面有老師的登入憑證，所以：所有字串經 `esc()`；章節名稱只用章節表（`data/math-kx-108.json`）裡的；卡片 id／章節 id／日期在伺服器和 App 兩邊都過格式檢查才會放進 HTML 屬性。selftest 有一項專測怪 id 被丟掉。
- CSP（`<meta http-equiv="Content-Security-Policy">`）：`connect-src` 只准本站＋這個 Supabase 專案，萬一被注入程式也送不出老師的登入資訊。單檔 App 仍需 `'unsafe-inline'`，所以 CSP 是第二道防線，第一道是 `esc()`。
- 換 Supabase 專案時，CSP 那行也要一起改（index.html 有註解）。

### T7 資料遺失：兩台互蓋、離線
- 一列一筆、每列各自「時間新的贏」：兩台改不同的節／卡都會留下；同一節兩台都改，後改的贏。
- 雲端是準的：只有「這台還沒上傳成功」的列才跟雲端比新舊；已上傳過的列一律照雲端那份（包含被雲端壓回的時間）。上傳成功後，剛送出的列也改用雲端回傳的版本。
  → 時鐘快的裝置不會「自己留著未來時間、永遠不收別台的修改」：雲端把它的時間壓回「現在＋10 分鐘」，這台跟著改，之後別台的正常修改它收得到（selftest 有一項專測這個情境）。
- 「還沒上傳」用時間比對記錄（`huikao.sync` 裡的 `synced`）：離線時改的東西，重開網頁也記得，有網路（`online`、切回 App）就補傳。
- 這台沒成功下載過雲端之前不上傳；這台已有紀錄、第一次接雲端 → 先問「合併」還是「以雲端為準」；換成另一位學生的連結 → 先問，取消就維持原本的學生。
- 剩餘風險：
  - 時間來自學生裝置的時鐘。若某台時鐘快很多，它的修改最多「贏」10 分鐘（雲端壓回時間，見 T4）；之後別台的修改照常蓋過、也會同步回這台。
  - 兩台離線各按一次「完成」同一節：次數各 +1，合併後只算一次（計畫書已判斷可接受）。
  - 刪除是軟刪除（`deleted=true`），列不會真的消失，所以「刪除」也能同步到另一台。

### T8 老師帳號與同網域
- 前提：專案 Email 自助註冊是關的。就算被打開，`hk_teachers` 名單也會擋住。
- `001_hk.sql` 從 `srs_teachers` 複製老師名單，最後列出 email 給你確認。
- 老師登入狀態存在瀏覽器 localStorage（key `huikao-teacher`），跟學生進度分開；共用電腦用完請按「登出」。
- 同網域注意：GitHub Pages 上同一個帳號的所有 App（例：`felixy-111.github.io/…`）共用同一個 localStorage 範圍。任何一個 App 若有 XSS 漏洞，理論上讀得到其他 App 的老師登入狀態與學生代碼。這是既有狀況（SRS App 也一樣），不是本次新增的；日後若要隔離，可改用自訂網域或子網域。

## 上線後必做：`002_verify_hk.sql`
001 跑完後，在 SQL Editor 貼上 `002_verify_hk.sql` 執行。它會假扮學生／老師／非老師三種身分實際測權限與合併規則，
最後**故意丟出錯誤讓所有測試資料自動復原**。看到「驗證全部通過」開頭的紅字＝成功；看到「FAIL」或其他錯誤＝把訊息截圖回報。

## 需要人工確認的假設
1. 專案的 Email 自助註冊仍是關閉的；匿名登入（Anonymous sign-ins）沒有打開。
2. `srs_teachers` 裡只有老師本人（001 檔尾會列出 hk_teachers 的 email）。
3. Supabase 專案是 Postgres 14 以上（`extract(epoch …)` 回傳精確小數，毫秒來回不失真；`gen_random_uuid()`、`sha256()` 是內建函式）。
4. `gen_random_uuid()` 使用 Postgres 的強亂數來源。
5. PostgREST 預設一次最多回 1000 列：老師端已分頁讀取（每次 1000 列）。
